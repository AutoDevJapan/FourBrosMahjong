## 全体構成(prd)

デプロイ構成の意思決定は [ADR-0001](../documents/adr/0001-deploy-architecture-and-preview-policy.md) が SSOT。要点は次の通り。

| レイヤ | プラットフォーム | 状態 |
|---|---|---|
| フロントエンド(現行アプリ全体) | **Vercel** | prd 稼働中(`four-bros-mahjong.vercel.app`) |
| オンライン対戦バックエンド(WebSocket) | **Railway** | repositoryでは`server/start.ts`をprocess entrypoint、liveness `/healthz`、readiness/healthcheck `/readyz`、対局接続 `/ws`として定義。Productionの実効設定はauthorized read-backまで未確認（HOLD） |
| 決済 | Stripe(方針) | 未着手 |

Next.js の画面は Vercel、オンライン対戦の長時間接続は Railway に分離する。process signalを所有する `server/start.ts` が `server/index.ts` のserver factoryを起動し、factory内の `RoomManager` がルームの権威状態を保持する。Vercel の `/online` 画面は WebSocket で接続する。現状は DB を持たないインメモリ構成のため、Railway の再起動・再デプロイで全ルームが破棄される。認証、永続化、複数インスタンス間の共有状態は将来の拡張とする。

## 昇格フロー（Option A選択後: prd → dev → stg）

1. 機能ブランチ(`feat/#N-*` 等)で実装し、`main` 宛に PR を作成 → レビュー・CI 通過後に `main` へマージ。
   - `main` は [issue #4](https://github.com/AutoDevJapan/FourBrosMahjong/issues/4) のブランチ保護により、直 push 禁止・必須ステータスチェック(`gitleaks`, `lint / typecheck / format / test / build`)通過が必須。
   - マージで Production へ自動デプロイする。
2. 検証済みの `main` snapshot を `dev` へ昇格: **同一 repository の `main` → `dev` PR**を作成し、CI 通過後に merge commit でマージする。
   - `dev` への push で Preview 環境(dev 用ブランチ URL)へ自動デプロイ。ここで動作確認。
3. `dev` の snapshot を `stg` へ昇格: **同一 repository の `dev` → `stg` PR**を作成し、CI 通過後に merge commit でマージする。
   - `stg` への push で `staging` カスタム環境へ自動デプロイ。ここで最終確認(本番相当データ・設定に近い状態での検証)。

各段階は「前段階の環境で確認が取れてから次へ進める」運用とし、`dev`/`stg` は保護ブランチにはしない(高速な巻き戻し・作り直しを許容する使い捨て可能なブランチとして扱う)。

### CI との対応

- CI([`.github/workflows/ci.yml`](../.github/workflows/ci.yml))は `main`・`dev`・`stg` の 3 ブランチを宛先とする PR、およびそれらへの push で実行される。上記フローの各段(feature→`main`、`main`→`dev`、`dev`→`stg`)はいずれも CI 通過が前提となる([issue #68](https://github.com/AutoDevJapan/FourBrosMahjong/issues/68))。
- `main`→`dev` / `dev`→`stg` は、各環境ブランチに過去の昇格 merge commit が残るため、push 前の宛先 tip が昇格元 head の祖先とは限らない。マージ後 push の重複 CI を安全に省略する証拠判定はこの2経路だけを特例とし、同一 repository の所定の昇格元、成功した trusted PR check、merge commit の親が「push 前の宛先 tip + 検証済み PR head」の順で一致すること、着地 tree が PR head と完全一致することをすべて要求する。任意の feature PR、親・tree の不一致、API/git 証拠不足では省略せず全検証を実行する。
- シークレットスキャン([`.github/workflows/gitleaks.yml`](../.github/workflows/gitleaks.yml))は宛先ブランチを問わず全 PR で実行されるため、昇格フローの全段をカバーする。

### GitHub Release と tag 保護

- Production 昇格の起点は上記のとおり **`main` へのマージ**であり、Vercel Git Integration が自動デプロイする。`vMAJOR.MINOR.PATCH` tag と GitHub Release は、公開済みの検証済み commit にバージョンを付ける後続の配布記録であり、Vercel デプロイの起点ではない。
- [`.github/workflows/release.yml`](../.github/workflows/release.yml) は公開権限を持たない `validate` job で、厳密な tag 形式、`package.json` / CHANGELOG、GitHub APIで捕捉した現在の `main` に対するtag commitのancestry、同じ SHA に対する本リポジトリの `ci.yml`・gitleaks・GitHub default CodeQL の成功を照合する。CodeQL は GitHub 管理の dynamic workflow と、その run に結合した GitHub Actions check suite の `actions` / `javascript-typescript` category を確認する。private repository の `GITHUB_TOKEN` は `contents: read`・`actions: read`・`checks: read` だけを使い、code-scanning analyses API や `security-events` 権限には依存しない。GitHub API の失敗、pending、失敗、証拠不足は公開不可として扱う。検証済みrelease notesは同一workflow runの固定名artifactとして渡し、後続の `contents: write` jobはcheckoutやrepository管理shellを実行せず、SHA固定のdownload/publisher Actionだけを実行する。この gate は後続の GitHub Release 公開だけを制御し、`main` merge 時点の Vercel Production 自動 deploy を待機・取消・再実行するものではない。
- GitHub Ruleset による `v*` tag 保護の担当ロール、設定、正常/拒否検証、break-glass、rollback は [Release tag 保護 runbook](../documents/guides/release-tag-protection-runbook.md) に定義する。2026-08-17 の follow-up 読み取り監査では不変性 ruleset `protect-existing-release-tags` (ID `20858931`) を `active` で適用し、`update` / `deletion` / `non_fast_forward` と空 bypass を確認した。repository 内の read-only helper (`.github/scripts/audit-release-tag-ruleset.mjs`) と validator で同じ契約を再確認できる。Release Operators Team・break-glass Team・緊急承認者は未決定のため、作成認可 ruleset は未適用である(issue #508)。リポジトリ内でレビュー・テスト可能な fail-closed guard は引き続き必須制御とする。

## 環境変数の管理方針

Vercel の Environment Variables は環境ごと(`Production` / `Preview` / `Development`)に分離して管理する。

- **Production**: `main`(prd)専用の値。本番シークレットはここにのみ設定する。オンライン対戦には `NEXT_PUBLIC_ONLINE_WS_URL` を設定する。
- **Preview**: PR ごとの Preview 全般に適用されるデフォルト値。必要に応じて「特定ブランチのみ」にスコープを絞れる(Vercel の Preview 環境変数は Git ブランチ単位で上書き可能)。オンライン対戦を Preview でも使う場合は、共有 Railway URL と、Railway 側の `ALLOWED_ORIGINS` に対象 Preview URL を追加する。
- **Development**: `vercel env pull` でローカル開発者が取得するローカル開発用の値。実際の外部サービスに影響しないダミー値を基本とする。
- 環境変数の値は Vercel/Railway 側で管理し、リポジトリにコミットしない(`.env*` は `.gitignore` 対象)。オンライン対戦の実装では、Vercel 側の接続先キー `NEXT_PUBLIC_ONLINE_WS_URL` と Railway 側の `ALLOWED_ORIGINS` を使用する。値が未設定のローカル開発では、Next.js 側は `ws://localhost:8080/ws` を既定値として利用するが、Production の接続先は必ず Vercel に `NEXT_PUBLIC_ONLINE_WS_URL` を設定する。

## バックエンド(Railway)疎通

オンライン対戦用の Railway サービスは現在リポジトリルートのdeprecatedな [`railway.json`](../railway.json)で構成する。2026-12-01のhard cutoffより前にInfrastructure as Codeへ移行するが、exact production targetと全resource inventoryをauthorized read-backするまでは、service名を公開domainから推測した手書き`.railway/railway.ts`を追加しない。full-project pull、manual ownership clear、legacy file保持、parity evidence、HOLD、contingencyは [Railway IaC ownership cutover parity evidence](../documents/guides/railway-iac-migration.md) に従う。

Production へ反映する際の fail-closed preflight、メンテナンス判断、Origin boundary probe、証跡、rollback は [Railway オンラインサーバー production deploy runbook](../documents/guides/railway-online-deploy-runbook.md) に従う。現行は active room 数を観測できず、再デプロイで全ルームが失われるため、runbook の `HOLD` 条件を満たさない状態で deploy してはならない。

- **Build**: `pnpm install --frozen-lockfile`
- **Start**: `node --import tsx server/start.ts`
- **Liveness**: `/healthz`（プロセス起動確認。drain/configurationのreadinessは判定しない）
- **Healthcheck / Readiness**: `/readyz`（repository上のhealthcheck指定値。Railway Productionの実効設定はauthorized read-backまで未確認。drain中や必須設定不正のinstanceをreadyにしない）
- **Port**: `PORT` は未設定時 `8080`。設定時は空値・`0`・小数・16進数・範囲外を許可せず、1〜65535のcanonicalな10進整数だけを受け付ける。
- **ルート案内**: `GET /` は `liveness: "/healthz"` と `readiness: "/readyz"` を返す。既存クライアント互換の `health: "/healthz"` は liveness の別名として維持する。
- **接続先**: WebSocket は `wss://<Railway公開ドメイン>/ws`。Vercel 側の `NEXT_PUBLIC_ONLINE_WS_URL` には同じ公開URLを設定する。
- **Origin**: Railway 側の `ALLOWED_ORIGINS` は、カンマ区切りの **canonical な完全一致 HTTP(S) Origin**（例: `https://four-bros-mahjong.vercel.app`、`http://localhost:3000`）だけを指定する。`*` や `https://*.vercel.app` のような wildcard、path（`/path`）・query（`?x=1`）付き、HTTP(S) 以外、その他の非canonical値は不可。先頭・末尾・連続するカンマによる空要素（例: `,https://example.com`、`https://example.com,`、`https://example.com,,https://other.example`）も不可。1件でも不正な値を混ぜた allowlist 全体を無効として fail-closed にし、`/readyz` は `503`、WebSocket handshake は有効そうな Origin を含めてすべて `403` とする。未設定・空の場合も同じ扱いとする。
- **状態**: ルーム・座席・対局状態はプロセス内メモリに保持する。再起動時のルーム消失は既知の制約であり、永続化が必要になった時点で DB/Redis を追加する。

Docker image の既定 `CMD` は、package manager を PID 1 にせず signal handler を持つ Node processへ直接届けるため、`node --import tsx server/start.ts` とする。production 相当imageでは1回だけbuildした同じimageを再利用し、PID 1、SIGTERM/SIGINT、1012 close、socket-close subdeadlineのforce、port/process消滅を `pnpm verify:server:container --image <local-image>` で検証する。この高コスト検証は通常PRのActionsでは常時実行しない。blocking roomを伴う総deadlineはcontrollerの決定的fake-clock testで固定し、このcontainer probeの証拠へ含めない。

[`railway.json`](../railway.json) の `startCommand` はDocker imageの既定commandと同じ `node --import tsx server/start.ts` に揃えている。Railwayの `startCommand` はimageの既定commandを上書きするため、このrepository変更だけではRailway productionのPID 1やsignal forwardingが実証されたとは扱わない。authorized operatorが実効command、PID/signal証拠、rollback targetをread-backできるまで、Railway deployとmaintenance flag有効化は **HOLD** とする。

## maintenance 通知の段階導入 (#726 / #728)

リポジトリ上の server には、手動 drain の core、認証済み `GET /ops/status`・`POST /ops/drain`・`DELETE /ops/drain`、`/readyz`、および接続中 client への additive maintenance 通知を実装している。通知と drain mutation は `ONLINE_MAINTENANCE_NOTICES_ENABLED=false` が既定で、設定が無効なままなら通常の create / join / resume / newGame 契約を変更しない。解除時の `accepting` は、認証済み DELETE が `draining` または `drained` から実際に状態を変更した場合だけ、現在 OPEN の socket へ exact payload として1回送る。

ただし、これは [issue #726](https://github.com/AutoDevJapan/FourBrosMahjong/issues/726) の段階実装である。リポジトリ上ではSIGTERM/SIGINTと固定total deadlineを結ぶgraceful shutdown controller、server生成のwall-clock drain/deadline timeline、およびauthenticated statusのsanitized replica/deployment identity fieldをlocal testで検証する。安全判断には引き続きmonotonic clockを使い、その値を時刻として外部公開しない。Railway productionの実効replica/deployment identity、direct Node start command・healthcheck・draining設定と実deployment read-backは未完である。この変更だけを根拠に Railway の flag、healthcheck、その他の設定を変更または有効化してはならない。

将来 server emission を有効化する前に、次をすべて満たす。満たせない場合は **HOLD** とし、Railway の変数変更や drain 操作を行わない。

- `draining` / `drained` / `terminating` と、手動 drain 解除を表す `accepting` を処理できる [issue #728](https://github.com/AutoDevJapan/FourBrosMahjong/issues/728) の client を先に Vercel Production へ配布し、reviewed full SHA と実 deployment の一致を記録する。
- #726 の残るRailway direct Node start command、production実効replica/deployment identity、healthcheck/draining設定、認証済みopsとの実deployment突合、production drain / rollback証跡を完成・レビューする。operatorがsanitizeしたnormalized evidenceは `pnpm verify:server:rollout-preflight` でoffline検証できるが、`pass`もproduction操作を承認せず、API真正性・active load・maintenance承認を証明しない。
- authorized operator が上記の証拠を確認した後にだけ flag を有効化する。client と server を同時に初回有効化しない。

旧 client は additive な `accepting` 通知を理解せず、安全に無視する。そのため、手動 drain を解除して server の `accepting` 復帰を認証済み status で確認した後もメンテナンス表示が残る利用者には、一度だけページを再読み込みするよう外部告知する。解除確認前の連続再読み込みは案内しない。再読み込みではブラウザメモリ上の snapshot をいったん失うが、同じタブの `sessionStorage` credential とインメモリ room が残っていれば、resume 後に server の最新 snapshot を再取得できる。再起動・再デプロイで失われた room は復元できない。

client を旧版へ rollback した場合も同じ reload guidance を使い、旧clientが解除通知で自動復帰するとは報告しない。`terminating` 後の解除や credential 復元は行わず、server rollback 自体もroomを復元しない。

## WebSocket の handshake timeout (#668)

upgrade後に`create` / `join` / `resume`を送らない未認証ソケットは、10秒でserverが`terminate()`する。これはprotocol pingへ応答するだけの未handshake接続が同時接続枠を占有し続けることを防ぐための上限であり、既にroomへ接続した座席のresume/reconnectやheartbeatには適用しない。通常のブラウザclientはWebSocketの`open`直後にroom requestを送るため影響しない。handshake前に切断された接続は既存の接続失敗・再試行導線で再接続できる。

## WebSocket の heartbeat (#666)

半開き接続を「接続済み」のまま残さないため、server/clientの両方でkeepaliveを行う。

- Railway serverは30秒ごとにWebSocket protocol pingを送り、直前のpingへのpongを受信できなかったpeerを `terminate()` する。`pong` 受信時は接続中の座席の `lastSeenAt` も更新する。
- ブラウザclientは接続中、15秒ごとにJSON `{"type":"ping"}`を送り、serverの `{"type":"pong"}` を45秒以内に受信できなければ現在のsocketを閉じ、既存の指数backoff再接続へ遷移する。再接続中は対局操作を無効化する。
- 通常のアイドル対局でも上記のkeepaliveが動く。application pingは既存のmessage rate limitの対象だが、通常間隔は制限値を十分下回る。
- serverのpeerがterminateされると通常の `close` cleanupで接続元枠を解放し、同席のreplacement socketがなければ座席を切断扱いにする。resume/reconnectのreplacementがある場合は、古いsocketのcloseが新しい接続状態を上書きしない。
- serverのheartbeat intervalは30秒、clientのintervalは15秒、clientの応答timeoutは45秒で、設定値はコードに固定している。これはネットワーク死活検知であり、Railway再起動時のインメモリルーム復元や複数プロセス間の状態共有は提供しない。

## WebSocket の abuse control (#641)

Railway のプロセス内で、認証前の `/ws` に次の固定上限を適用する。数値は「4人の通常対局、同一家庭/共有回線、ブラウザの再接続」を許容しつつ、1プロセスのメモリ・CPU・ルーム生成を無制限にしないための第一段階である。

| 対象 | 上限 | 単位/窓 | 超過時 |
|---|---:|---|---|
| 同時 WebSocket 接続 | 256 | プロセス全体 | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 同時接続 | 32 | Node が見た接続元ごと | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 接続試行 | 60 | 接続元ごと / 10秒 | HTTP 429 + `code: rate_limited`, `scope: connection` |
| ルーム作成 | 5 | 接続元ごと / 10分 | WebSocket `error`、`scope: create` |
| ルーム参加 | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: join` |
| 再接続(resume) | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: resume` |
| メッセージ | 240 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作(`action`/`newGame`) | 120 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |
| メッセージ合計 | 600 | 接続元ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作合計 | 300 | 接続元ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |

上限エラーは機械判定可能な安定コード(`connection_limit` / `rate_limited`)と、再試行までの目安を示す `retryAfterMs` を返す。確立済み接続ではエラー送信後に close `1013`(Try Again Later)で切断し、クライアントは既存の再接続導線から再試行できる。アップグレード前の拒否は WebSocket フレームを送れないため、HTTP ステータス・JSON・`Retry-After` で同じ契約を提供する。拒否したアップグレードソケットと切断済みクライアントは直ちに解放し、期限切れの接続元バケットも定期 sweep で削除する。

接続元はクライアントが自由に指定できるヘッダではなく、Node の `request.socket.remoteAddress`(IPv4-mapped IPv6 は正規化)を使う。したがって、信頼できる proxy の IP 転送設定を前提にしていない。proxy の内側で全利用者が同一アドレスに見える場合でも、256接続のプロセス全体上限と4人対局に十分な接続元上限が残る。現行の `MAX_ROOMS=1,000` とメッセージサイズ上限32 KiBも併用する。

これらは単一 Railway プロセス内の best-effort 制御であり、Railway/外部 proxy の帯域・WAF・分散インスタンス間で共有されるクォータを暗黙に仮定しない。複数インスタンス展開、信頼できる proxy 連携、認証/アカウント単位のクォータ、永続的な観測・ban は別 issue のフォローアップとする。
