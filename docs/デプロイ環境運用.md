# デプロイ・環境運用方針(Vercel / Railway)

[issue #3](https://github.com/AutoDevJapan/FourBrosMahjong/issues/3) の受け入れ基準に基づき、Vercel 連携・Preview 環境・dev/stg/prd の昇格フローを定義する。加えて [issue #69](https://github.com/AutoDevJapan/FourBrosMahjong/issues/69) で、バックエンド(Railway)とカスタムドメインの位置づけを実態に合わせて明記する。

## 全体構成(prd)

デプロイ構成の意思決定は [ADR-0001](../documents/adr/0001-deploy-architecture-and-preview-policy.md) が SSOT。要点は次の通り。

| レイヤ | プラットフォーム | 状態 |
|---|---|---|
| フロントエンド(現行アプリ全体) | **Vercel** | prd 稼働中(`four-bros-mahjong.vercel.app`) |
| オンライン対戦バックエンド(WebSocket) | **Railway** | `server/index.ts` を常駐プロセスとして稼働。ヘルスチェック `/healthz`、対局接続 `/ws` |
| 決済 | Stripe(方針) | 未着手 |

Next.js の画面は Vercel、オンライン対戦の長時間接続は Railway に分離する。Railway の `server/index.ts` がルームの権威状態を保持し、Vercel の `/online` 画面が WebSocket で接続する。現状は DB を持たないインメモリ構成のため、Railway の再起動・再デプロイで全ルームが破棄される。認証、永続化、複数インスタンス間の共有状態は将来の拡張とする。

## Vercel プロジェクト連携

- Vercel プロジェクト `four-bros-mahjong`(チーム: Masashi Matsumoto's projects)を GitHub リポジトリ `AutoDevJapan/FourBrosMahjong` と Git Integration で連携済み。
- Pull Request Comments を有効化済み — PR ごとに Preview デプロイの URL が自動でコメントされる。
- Framework Preset は `Next.js` を自動検出。Install/Build Command は Vercel の zero-config 検出に任せる(`pnpm-lock.yaml` の存在から pnpm を自動選択するため、明示的な Override は設定しない)。
- Node.js バージョンは Vercel が `package.json` の `engines.node`(`^22.22.2 || ^24.15.0 || >=26`、[issue #1](https://github.com/AutoDevJapan/FourBrosMahjong/issues/1) で導入)を自動的に参照する。プロジェクト側で個別に固定しない。パッチ下限は devDependency の `jsdom@30` が要求する `^22.22.2 || ^24.15.0 || >=26.0.0` に合わせている(`.npmrc` の `engine-strict=true` により、下限未満の Node では `pnpm install` が `ERR_PNPM_UNSUPPORTED_ENGINE` で失敗するため、`engines.node` が実際の下限より緩いと宣言と実態が乖離する)。
- 関数実行リージョンはリポジトリルートの [`vercel.json`](../vercel.json) で **東京(`hnd1`)** を指定している([issue #276](https://github.com/AutoDevJapan/FourBrosMahjong/issues/276))。全ルートが動的レンダリング(リクエスト毎の CSP nonce 発行)で毎回サーバー関数が実行されるため、既定の `iad1`(米国東部)のままだと日本ユーザーの TTFB に +150〜200ms の往復レイテンシが乗る。単一リージョン指定のためプラン範囲内であり、ダッシュボード設定ではなく `vercel.json` に置くことで IaC として再現性を担保する。

## 環境定義

Vercel の Environments 機能([Settings > Environments](https://vercel.com/masashi-matsumotos-projects-c5830f3d/four-bros-mahjong/settings/environments))でブランチと環境を紐付ける。

| 環境 | 役割 | ブランチ | Vercel Environment | URL |
|---|---|---|---|---|
| **prd** | Production。実運用相当 | `main` | `Production`(組み込み) | `four-bros-mahjong.vercel.app`(カスタムドメインは未割当。公開手順は [カスタムドメイン公開手順](../documents/guides/custom-domain-setup.md)) |
| **stg** | Staging。本番反映前の最終確認 | `stg` | カスタム環境 `staging`(Branch Tracking: `stg`) | `https://four-bros-mahjong-git-stg-<team>.vercel.app`(ブランチ Push で自動生成) |
| **dev** | Development。開発中の統合確認 | `dev` | `Preview`(組み込み、未割当ブランチとして扱う) | `https://four-bros-mahjong-git-dev-<team>.vercel.app`(ブランチ Push で自動生成) |
| PRごと | 機能単位のレビュー用 | 各 `feat/#N-*` 等 | `Preview` | PR に自動コメントされる一意の Preview URL |

`dev`/`stg` は GitHub 上の永続ブランチとして作成済み(`main` から分岐)。それぞれへの push で Vercel が対応する環境へ自動デプロイする。

## 昇格フロー(prd → dev → stg)

1. 機能ブランチ(`feat/#N-*` 等)で実装し、`main` 宛に PR を作成 → レビュー・CI 通過後に `main` へマージ。
   - `main` は [issue #4](https://github.com/AutoDevJapan/FourBrosMahjong/issues/4) のブランチ保護により、直 push 禁止・必須ステータスチェック(`gitleaks`, `lint / typecheck / format / test / build`)通過が必須。
   - マージで Production へ自動デプロイする。
2. 検証済みの `main` snapshot を `dev` へ昇格: **同一 repository の `main` → `dev` PR**を作成し、CI 通過後に merge commit でマージする。
   - `dev` への push で Preview 環境(dev 用ブランチ URL)へ自動デプロイ。ここで動作確認。
3. `dev` の snapshot を `stg` へ昇格: **同一 repository の `dev` → `stg` PR**を作成し、CI 通過後に merge commit でマージする。
   - `stg` への push で `staging` カスタム環境へ自動デプロイ。ここで最終確認(本番相当データ・設定に近い状態での検証)。

各段階は「前段階の環境で確認が取れてから次へ進める」運用とし、`dev`/`stg` は保護ブランチにはしない(高速な巻き戻し・作り直しを許容する使い捨て可能なブランチとして扱う)。

### CI との対応

- CI([`.github/workflows/ci.yml`](../.github/workflows/ci.yml))は `main`・`dev`・`stg` の 3 ブランチを宛先とする PR、およびそれらへの push で実行される。上記フローの各段(feature→`main`、`main`→`dev`、`dev`→`stg`)はいずれも CI 通過が前提となる([issue #68](https://github.com/AutoDevJapan/FourBrosMahjong/issues/68))。
- `main`→`dev` / `dev`→`stg` は、各環境ブランチに過去の昇格 merge commit が残るため、push 前の宛先 tip が昇格元 head の祖先とは限らない。マージ後 push の重複 CI を安全に省略する証拠判定はこの2経路だけを特例とし、同一 repository の所定の昇格元、成功した trusted PR check、merge commit の親が「push 前の宛先 tip + 検証済み PR head」の順で一致すること、着地 tree が PR head と完全一致することをすべて要求する。任意の feature PR、親・tree の不一致、API/git 証拠不足では省略せず全検証を実行する。
- シークレットスキャン([`.github/workflows/gitleaks.yml`](../.github/workflows/gitleaks.yml))は宛先ブランチを問わず全 PR で実行されるため、昇格フローの全段をカバーする。

### GitHub Release と tag 保護

- Production 昇格の起点は上記のとおり **`main` へのマージ**であり、Vercel Git Integration が自動デプロイする。`vMAJOR.MINOR.PATCH` tag と GitHub Release は、公開済みの検証済み commit にバージョンを付ける後続の配布記録であり、Vercel デプロイの起点ではない。
- [`.github/workflows/release.yml`](../.github/workflows/release.yml) は公開権限を持たない `validate` job で、厳密な tag 形式、`package.json` / CHANGELOG、tag commit の `origin/main` ancestry、同じ SHA に対する本リポジトリの `ci.yml` の成功を照合する。GitHub API の失敗や証拠不足は公開不可として扱い、成功後の別 job にだけ `contents: write` を付与する。
- GitHub Ruleset による `v*` tag 保護の担当ロール、設定、正常/拒否検証、break-glass、rollback は [Release tag 保護 runbook](../documents/guides/release-tag-protection-runbook.md) に定義する。2026-08-17 の follow-up 読み取り監査では不変性 ruleset `protect-existing-release-tags` (ID `20858931`) を `active` で適用し、`update` / `deletion` / `non_fast_forward` と空 bypass を確認した。repository 内の read-only helper (`.github/scripts/audit-release-tag-ruleset.mjs`) と validator で同じ契約を再確認できる。Release Operators Team・break-glass Team・緊急承認者は未決定のため、作成認可 ruleset は未適用である(issue #508)。リポジトリ内でレビュー・テスト可能な fail-closed guard は引き続き必須制御とする。

## 環境変数の管理方針

Vercel の Environment Variables は環境ごと(`Production` / `Preview` / `Development`)に分離して管理する。

- **Production**: `main`(prd)専用の値。本番シークレットはここにのみ設定する。オンライン対戦には `NEXT_PUBLIC_ONLINE_WS_URL` を設定する。
- **Preview**: PR ごとの Preview 全般に適用されるデフォルト値。必要に応じて「特定ブランチのみ」にスコープを絞れる(Vercel の Preview 環境変数は Git ブランチ単位で上書き可能)。オンライン対戦を Preview でも使う場合は、共有 Railway URL と、Railway 側の `ALLOWED_ORIGINS` に対象 Preview URL を追加する。
- **Development**: `vercel env pull` でローカル開発者が取得するローカル開発用の値。実際の外部サービスに影響しないダミー値を基本とする。
- 環境変数の値は Vercel/Railway 側で管理し、リポジトリにコミットしない(`.env*` は `.gitignore` 対象)。オンライン対戦の実装では、Vercel 側の接続先キー `NEXT_PUBLIC_ONLINE_WS_URL` と Railway 側の `ALLOWED_ORIGINS` を使用する。値が未設定のローカル開発では、Next.js 側は `ws://localhost:8080/ws` を既定値として利用するが、Production の接続先は必ず Vercel に `NEXT_PUBLIC_ONLINE_WS_URL` を設定する。

## バックエンド(Railway)疎通

オンライン対戦用の Railway サービスはリポジトリルートの [`railway.json`](../railway.json)で構成する。

- **Build**: `pnpm install --frozen-lockfile`
- **Start**: `pnpm server:start`
- **Healthcheck**: `/healthz`
- **接続先**: WebSocket は `wss://<Railway公開ドメイン>/ws`。Vercel 側の `NEXT_PUBLIC_ONLINE_WS_URL` には同じ公開URLを設定する。
- **Origin**: Railway 側の `ALLOWED_ORIGINS` に Vercel 本番URLをカンマ区切りで設定する。空の場合は開発・初期疎通用に全 Origin を許可する。
- **状態**: ルーム・座席・対局状態はプロセス内メモリに保持する。再起動時のルーム消失は既知の制約であり、永続化が必要になった時点で DB/Redis を追加する。

## WebSocket の heartbeat (#666)

半開き接続を「接続済み」のまま残さないため、server/clientの両方でkeepaliveを行う。

- Railway serverは30秒ごとにWebSocket protocol pingを送り、直前のpingへのpongを受信できなかったpeerを `terminate()` する。`pong` 受信時は接続中の座席の `lastSeenAt` も更新する。
- ブラウザclientは接続中、15秒ごとにJSON `{"type":"ping"}`を送り、serverの `{"type":"pong"}` を45秒以内に受信できなければ現在のsocketを閉じ、既存の指数backoff再接続へ遷移する。再接続中は対局操作を無効化する。
- 通常のアイドル対局でも上記のkeepaliveが動く。application pingは既存のmessage rate limitの対象だが、通常間隔は制限値を十分下回る。
- serverのpeerがterminateされると通常の `close` cleanupで接続元枠を解放し、同席のreplacement socketがなければ座席を切断扱いにする。resume/reconnectのreplacementがある場合は、古いsocketのcloseが新しい接続状態を上書きしない。
- serverのheartbeat intervalは30秒、clientのintervalは15秒、clientの応答timeoutは45秒で、設定値はコードに固定している。これはネットワーク死活検知であり、Railway再起動時のインメモリルーム復元や複数プロセス間の状態共有は提供しない。

## WebSocket の abuse control (#641)

Railway のプロセス内で、認証前の `/ws` に次の固定上限を適用する。数値は「4人の通常対局、同一家庭/共有回線、ブラウザの再接続」を許容しつつ、1プロセスのメモリ・CPU・ルーム生成を無制限にしないための第一段階である。

| 対象 | 上限 | 単位/窓 | 超過時 |
|---|---:|---|---|
| 同時 WebSocket 接続 | 256 | プロセス全体 | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 同時接続 | 32 | Node が見た接続元ごと | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 接続試行 | 60 | 接続元ごと / 10秒 | HTTP 429 + `code: rate_limited`, `scope: connection` |
| ルーム作成 | 5 | 接続元ごと / 10分 | WebSocket `error`、`scope: create` |
| ルーム参加 | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: join` |
| 再接続(resume) | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: resume` |
| メッセージ | 240 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作(`action`/`newGame`) | 120 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |
| メッセージ合計 | 600 | 接続元ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作合計 | 300 | 接続元ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |

上限エラーは機械判定可能な安定コード(`connection_limit` / `rate_limited`)と、再試行までの目安を示す `retryAfterMs` を返す。確立済み接続ではエラー送信後に close `1013`(Try Again Later)で切断し、クライアントは既存の再接続導線から再試行できる。アップグレード前の拒否は WebSocket フレームを送れないため、HTTP ステータス・JSON・`Retry-After` で同じ契約を提供する。拒否したアップグレードソケットと切断済みクライアントは直ちに解放し、期限切れの接続元バケットも定期 sweep で削除する。

接続元はクライアントが自由に指定できるヘッダではなく、Node の `request.socket.remoteAddress`(IPv4-mapped IPv6 は正規化)を使う。したがって、信頼できる proxy の IP 転送設定を前提にしていない。proxy の内側で全利用者が同一アドレスに見える場合でも、256接続のプロセス全体上限と4人対局に十分な接続元上限が残る。現行の `MAX_ROOMS=1,000` とメッセージサイズ上限32 KiBも併用する。

これらは単一 Railway プロセス内の best-effort 制御であり、Railway/外部 proxy の帯域・WAF・分散インスタンス間で共有されるクォータを暗黙に仮定しない。複数インスタンス展開、信頼できる proxy 連携、認証/アカウント単位のクォータ、永続的な観測・ban は別 issue のフォローアップとする。
