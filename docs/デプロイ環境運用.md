# デプロイ・環境運用方針(Vercel / Railway)

[issue #3](https://github.com/AutoDevJapan/FourBrosMahjong/issues/3) の受け入れ基準に基づき、Vercel 連携・Preview 環境・dev/stg/prd の昇格フローを定義する。加えて [issue #69](https://github.com/AutoDevJapan/FourBrosMahjong/issues/69) で、バックエンド(Railway)とカスタムドメインの位置づけを実態に合わせて明記する。

## 全体構成(prd)

デプロイ構成の意思決定は [ADR-0001](../documents/adr/0001-deploy-architecture-and-preview-policy.md) が SSOT。要点は次の通り。

| レイヤ | プラットフォーム | 状態 |
|---|---|---|
| フロントエンド(現行アプリ全体) | **Vercel** | prd 稼働中(`four-bros-mahjong.vercel.app`) |
| バックエンド(API/DB) | **Railway**(将来配置先として確定) | **未疎通**。現時点でバックエンドは未実装のため Railway 上にリソースを作成していない |
| 決済 | Stripe(方針) | 未着手 |

現行アプリは Next.js フロントエンドのみで、サーバーサイドの永続状態を持つバックエンドは存在しない。`config.godd`(`infra: [..., vercel, railway]`)と `AGENTS.md` のスタック定義に含まれる `railway` は、**バックエンドが必要になった時点の prd 配置先**を指す(新たな課金要因を今は増やさないため、実際の疎通は着手時の別 issue で行う)。Railway の具体的なプロジェクト作成・環境変数・接続方針(CORS 等)はその issue で文書化する。

## Vercel プロジェクト連携

- Vercel プロジェクト `four-bros-mahjong`(チーム: Masashi Matsumoto's projects)を GitHub リポジトリ `AutoDevJapan/FourBrosMahjong` と Git Integration で連携済み。
- Pull Request Comments を有効化済み — PR ごとに Preview デプロイの URL が自動でコメントされる。
- Framework Preset は `Next.js` を自動検出。Install/Build Command は Vercel の zero-config 検出に任せる(`pnpm-lock.yaml` の存在から pnpm を自動選択するため、明示的な Override は設定しない)。
- Node.js バージョンは Vercel が `package.json` の `engines.node`(`^22.22.2 || ^24.15.0 || >=26`、[issue #1](https://github.com/AutoDevJapan/FourBrosMahjong/issues/1) で導入)を自動的に参照する。プロジェクト側で個別に固定しない。パッチ下限は devDependency の `jsdom@30` が要求する `^22.22.2 || ^24.15.0 || >=26.0.0` に合わせている(`.npmrc` の `engine-strict=true` により、下限未満の Node では `pnpm install` が `ERR_PNPM_UNSUPPORTED_ENGINE` で失敗するため、`engines.node` が実際の下限より緩いと宣言と実態が乖離する)。
- 関数実行リージョンはリポジトリルートの [`vercel.json`](../vercel.json) で **東京(`hnd1`)** を指定している([issue #276](https://github.com/AutoDevJapan/FourBrosMahjong/issues/276))。全ルートが動的レンダリング(リクエスト毎の CSP nonce 発行)で毎回サーバー関数が実行されるため、既定の `iad1`(米国東部)のままだと日本ユーザーの TTFB に +150〜200ms の往復レイテンシが乗る。単一リージョン指定のためプラン範囲内であり、ダッシュボード設定ではなく `vercel.json` に置くことで IaC として再現性を担保する。

## 環境定義

Vercel の Environments 機能([Settings > Environments](https://vercel.com/masashi-matsumotos-projects-c5830f3d/four-bros-mahjong/settings/environments))でブランチと環境を紐付ける。

| 環境 | 役割 | ブランチ | Vercel Environment | URL |
|---|---|---|---|---|
| **prd** | Production。実運用相当 | `main` | `Production`(組み込み) | `four-bros-mahjong.vercel.app`(カスタムドメインは未割当。公開手順は [カスタムドメイン公開手順](../documents/guides/custom-domain-setup.md)) |
| **stg** | Staging。本番反映前の最終確認 | `stg` | カスタム環境 `staging`(Branch Tracking: `stg`) | `https://four-bros-mahjong-git-stg-<team>.vercel.app`(ブランチ Push で自動生成) |
| **dev** | Development。開発中の統合確認 | `dev` | `Preview`(組み込み、未割当ブランチとして扱う) | `https://four-bros-mahjong-git-dev-<team>.vercel.app`(ブランチ Push で自動生成) |
| PRごと | 機能単位のレビュー用 | 各 `feat/#N-*` 等 | `Preview` | PR に自動コメントされる一意の Preview URL |

`dev`/`stg` は GitHub 上の永続ブランチとして作成済み(`main` から分岐)。それぞれへの push で Vercel が対応する環境へ自動デプロイする。

## 昇格フロー(dev → stg → prd)

1. 機能ブランチ(`feat/#N-*` 等)で実装し、`dev` 宛に PR を作成 → レビュー・CI 通過後に `dev` へマージ。
   - `dev` への push で Preview 環境(dev 用ブランチ URL)へ自動デプロイ。ここで動作確認。
2. `dev` の変更を `stg` へ昇格: `dev` → `stg` への PR(または fast-forward マージ)を作成し、CI 通過後にマージ。
   - `stg` への push で `staging` カスタム環境へ自動デプロイ。ここで最終確認(本番相当データ・設定に近い状態での検証)。
3. `stg` の変更を `main`(prd)へ昇格: `stg` → `main` への PR を作成する。
   - `main` は [issue #4](https://github.com/AutoDevJapan/FourBrosMahjong/issues/4) のブランチ保護により、直 push 禁止・必須ステータスチェック(`gitleaks`, `lint / typecheck / format / test / build`)通過が必須。
   - マージで Production へ自動デプロイ。

各段階は「前段階の環境で確認が取れてから次へ進める」運用とし、`dev`/`stg` は保護ブランチにはしない(高速な巻き戻し・作り直しを許容する使い捨て可能なブランチとして扱う)。

### CI との対応

- CI([`.github/workflows/ci.yml`](../.github/workflows/ci.yml))は `main`・`dev`・`stg` の 3 ブランチを宛先とする PR、およびそれらへの push で実行される。上記フローの各段(feature→`dev`、`dev`→`stg`、`stg`→`main`)はいずれも CI 通過が前提となる([issue #68](https://github.com/AutoDevJapan/FourBrosMahjong/issues/68))。
- シークレットスキャン([`.github/workflows/gitleaks.yml`](../.github/workflows/gitleaks.yml))は宛先ブランチを問わず全 PR で実行されるため、昇格フローの全段をカバーする。

### GitHub Release と tag 保護

- Production 昇格の起点は上記のとおり **`main` へのマージ**であり、Vercel Git Integration が自動デプロイする。`vMAJOR.MINOR.PATCH` tag と GitHub Release は、公開済みの検証済み commit にバージョンを付ける後続の配布記録であり、Vercel デプロイの起点ではない。
- [`.github/workflows/release.yml`](../.github/workflows/release.yml) は公開権限を持たない `validate` job で、厳密な tag 形式、`package.json` / CHANGELOG、tag commit の `origin/main` ancestry、同じ SHA に対する本リポジトリの `ci.yml` の成功を照合する。GitHub API の失敗や証拠不足は公開不可として扱い、成功後の別 job にだけ `contents: write` を付与する。
- GitHub Ruleset による `v*` tag 保護の担当ロール、推奨設定、正常/拒否検証、break-glass、rollback は [Release tag 保護 runbook](../documents/guides/release-tag-protection-runbook.md) に定義する。2026-08-12 の読み取り監査時点では ruleset は未導入で、Release Operators Team と緊急承認者も未決定であるため、外部設定を導入済みとは扱わない(issue #508)。リポジトリ内でレビュー・テスト可能な fail-closed guard は引き続き必須制御とする。

## 環境変数の管理方針

Vercel の Environment Variables は環境ごと(`Production` / `Preview` / `Development`)に分離して管理する。

- **Production**: `main`(prd)専用の値。本番シークレットはここにのみ設定する。
- **Preview**: PR ごとの Preview 全般に適用されるデフォルト値。必要に応じて「特定ブランチのみ」にスコープを絞れる(Vercel の Preview 環境変数は Git ブランチ単位で上書き可能) — `stg` ブランチに本番相当の値を使いたい場合はこの機能でスコープする。
- **Development**: `vercel env pull` でローカル開発者が取得するローカル開発用の値。実際の外部サービスに影響しないダミー値を基本とする。
- 環境変数は Vercel 側のみで管理し、リポジトリにコミットしない(`.env*` は `.gitignore` 対象)。現時点(create-next-app 直後の足場段階)ではアプリ側の環境変数は存在しないため、実際の値の追加は必要になった時点で上記方針に従って行う。

本番をカスタムドメインで公開する場合の手順(Vercel へのドメイン追加・DNS 設定・SSL・検証)は [カスタムドメイン公開手順](../documents/guides/custom-domain-setup.md) にまとめている。2026-07-17 時点では `four-bros-mahjong.vercel.app` のみで、カスタムドメインは未割当。ドメインを確定・割当した後は、上表 prd 行の URL を実ドメインに更新する。

## バックエンド(Railway)疎通

現時点でバックエンドは未実装のため、Railway 上に本プロジェクトのサービスは存在しない([ADR-0001](../documents/adr/0001-deploy-architecture-and-preview-policy.md))。バックエンドが必要になった時点で、別 issue にて以下を具体化・文書化する。

- Railway プロジェクト/サービスの作成と環境(dev/stg/prd)分離。
- 環境変数の管理境界(Vercel フロント ↔ Railway バックエンド、Stripe など外部サービスのシークレット)。
- フロント(Vercel カスタムドメイン)からバックエンド API を呼ぶ際の接続方針(API URL の環境変数管理・CORS 許可オリジン)。
