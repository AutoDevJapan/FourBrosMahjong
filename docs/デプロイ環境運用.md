2. 同じheadの必須CIと別モデルレビューを確認し、必要な指摘を修正してマージする。人間レビューを明示要求する規則がある場合は従う。現在のmain保護は承認数0で、PRと必須CIを要求している。

## バックエンド(Railway)疎通

オンライン対戦用の Railway サービスは、既存Productionの対象サービスだけを宣言する [named partial](../.railway/railway.ts) で管理する。対象は認証済みread-backで照合し、CLI 5.71.0のlocal migrateで生成したsourceを保持している。共有projectの他サービスと変数は管理対象へ追加しない。2026-12-01のhard cutoff、SDK 3.16.0との型互換、所有権移行とruntime更新の分離、planの検証、rollbackは [Railway IaC移行手順](../documents/guides/railway-iac-migration.md) に従う。local生成とplan成功だけでは、外部cutover・apply・本番反映の完了を意味しない。旧root設定は[`railway-readyz-before-iac.json`](../documents/fixtures/railway-readyz-before-iac.json)へ同じbytesで保存し、rootには置かない。2026-11-10の新snapshotでは旧file参照不在を確認した。次の配布でも、その候補の実効設定とfile参照を改めて照合する。

Production へ反映する際のpreflight、メンテナンス判断、Origin boundary probe、証跡、rollbackは[Railway オンラインサーバー production deploy runbook](../documents/guides/railway-online-deploy-runbook.md)に従う。現在のruntimeは認証済み`GET /ops/status`でroom集計を取得できる。ルームは引き続きメモリ上だけに存在し、更新の直前にloadと受付条件を確認する。

- **Build**: [Dockerfile](../Dockerfile)のオンライン専用multi-stage build。runtime workspaceだけをfrozen lockfileでinstall/deployする。
- **Start**: `node --import tsx server/start.ts`
- **Liveness**: `/healthz`（プロセス起動確認。drain/configurationのreadinessは判定しない）
- **Healthcheck / Readiness**: `/readyz`（2026-11-09にProductionの実効設定と200応答を確認。drain中や必須設定不正のinstanceをreadyにしない）
- **Port**: `PORT` は未設定時 `8080`。設定時は空値・`0`・小数・16進数・範囲外を許可せず、1〜65535のcanonicalな10進整数だけを受け付ける。
- **ルート案内**: `GET /` は `liveness: "/healthz"` と `readiness: "/readyz"` を返す。既存クライアント互換の `health: "/healthz"` は liveness の別名として維持する。
- **接続先**: WebSocket は `wss://<Railway公開ドメイン>/ws`。Vercel 側の `NEXT_PUBLIC_ONLINE_WS_URL` には同じ公開URLを設定する。
- **Origin**: Railway 側の `ALLOWED_ORIGINS` は、カンマ区切りの **canonical な完全一致 HTTP(S) Origin**（例: `https://four-bros-mahjong.vercel.app`、`http://localhost:3000`）だけを指定する。`*` や `https://*.vercel.app` のような wildcard、path（`/path`）・query（`?x=1`）付き、HTTP(S) 以外、その他の非canonical値は不可。先頭・末尾・連続するカンマによる空要素（例: `,https://example.com`、`https://example.com,`、`https://example.com,,https://other.example`）も不可。1件でも不正な値を混ぜた allowlist 全体を無効として fail-closed にし、`/readyz` は `503`、WebSocket handshake は有効そうな Origin を含めてすべて `403` とする。未設定・空の場合も同じ扱いとする。
- **状態**: ルーム・座席・対局状態はプロセス内メモリに保持する。再起動時のルーム消失は既知の制約であり、永続化が必要になった時点で DB/Redis を追加する。

Docker image の既定 `CMD` は、package manager を PID 1 にせず signal handler を持つ Node processへ直接届けるため、`node --import tsx server/start.ts` とする。production 相当imageでは1回だけbuildした同じimageを再利用し、PID 1、SIGTERM/SIGINT、1012 close、socket-close subdeadlineのforce、port/process消滅を `pnpm verify:server:container --image <local-image>` で検証する。この高コスト検証は通常PRのActionsでは常時実行しない。blocking roomを伴う総deadlineはcontrollerの決定的fake-clock testで固定し、このcontainer probeの証拠へ含めない。

[`.railway/railway.ts`](../.railway/railway.ts)の起動設定とDocker imageの既定commandは`node --import tsx server/start.ts`で一致する。2026-11-09 22:29 JSTのsource `a976d46ca044efe20241b5d939a98d064b1c1969`では実効command、PID 1とUID/GID 1000、対象deploymentのidentityを照合した。signal終了は同じruntime経路のproduction相当imageで確認した。次回更新でもそのsourceと実効設定を確認し、過去のread-backだけで新しい候補や現在のloadを確認済みとしない。

## maintenance 通知の段階導入 (#726 / #728)

リポジトリ上の server には、手動 drain の core、認証済み `GET /ops/status`・`POST /ops/drain`・`DELETE /ops/drain`、`/readyz`、および接続中 client への additive maintenance 通知を実装している。通知と drain mutation は `ONLINE_MAINTENANCE_NOTICES_ENABLED=false` が既定で、設定が無効なままなら通常の create / join / resume / newGame 契約を変更しない。解除時の `accepting` は、認証済み DELETE が `draining` または `drained` から実際に状態を変更した場合だけ、現在 OPEN の socket へ exact payload として1回送る。

これは[issue #726](https://github.com/AutoDevJapan/FourBrosMahjong/issues/726)の段階導入である。2026-11-09には実効replica/deployment identity、direct Node start command、healthcheck、draining設定をread-backした。SIGTERM/SIGINTと固定total deadlineは同じruntime経路のproduction相当imageで確認した。同日22:29 JSTの[追加受入](../documents/evidence/production-online-20261109.md)では通知の有効化、正規drain後のsource upload、new runtimeのaccepting復帰とroom/接続0を確認した。接続clientが無かったため通知payloadの本番受信は未観測、実rollbackも未実施として分けて残す。安全判断には引き続きmonotonic clockを使い、その値を時刻として外部公開しない。

将来 server emission を有効化する前に、次をすべて満たす。満たせない場合は **HOLD** とし、Railway の変数変更や drain 操作を行わない。

- `draining` / `drained` / `terminating` と、手動 drain 解除を表す `accepting` を処理できる [issue #728](https://github.com/AutoDevJapan/FourBrosMahjong/issues/728) の client を先に Vercel Production へ配布し、reviewed full SHA と実 deployment の一致を記録する。
- #726 の残るRailway direct Node start command、production実効replica/deployment identity、healthcheck/draining設定、認証済みopsとの実deployment突合、production drain / rollback証跡を完成・レビューする。operatorがsanitizeしたnormalized evidenceは `pnpm verify:server:rollout-preflight` でoffline検証できるが、`pass`もproduction操作を承認せず、API真正性・active load・maintenance承認を証明しない。
- authorized operator が上記の証拠を確認した後にだけ flag を有効化する。client と server を同時に初回有効化しない。

旧 client は additive な `accepting` 通知を理解せず、安全に無視する。そのため、手動 drain を解除して server の `accepting` 復帰を認証済み status で確認した後もメンテナンス表示が残る利用者には、一度だけページを再読み込みするよう外部告知する。解除確認前の連続再読み込みは案内しない。再読み込みではブラウザメモリ上の snapshot をいったん失うが、同じタブの `sessionStorage` credential とインメモリ room が残っていれば、resume 後に server の最新 snapshot を再取得できる。再起動・再デプロイで失われた room は復元できない。

client を旧版へ rollback した場合も同じ reload guidance を使い、旧clientが解除通知で自動復帰するとは報告しない。`terminating` 後の解除や credential 復元は行わず、server rollback 自体もroomを復元しない。

## WebSocket の handshake timeout (#668)

upgrade後に`create` / `join` / `resume`を送らない未認証ソケットは、10秒でserverが`terminate()`する。これはprotocol pingへ応答するだけの未handshake接続が同時接続枠を占有し続けることを防ぐための上限であり、既にroomへ接続した座席のresume/reconnectやheartbeatには適用しない。通常のブラウザclientはWebSocketの`open`直後にroom requestを送るため影響しない。handshake前に切断された接続は既存の接続失敗・再試行導線で再接続できる。

## WebSocket の heartbeat (#666)

半開き接続を「接続済み」のまま残さないため、server/clientの両方でkeepaliveを行う。

- Railway serverは30秒ごとにWebSocket protocol pingを送り、直前のpingへのpongを受信できなかったpeerを `terminate()` する。`pong` 受信時は接続中の座席の `lastSeenAt` も更新する。
- ブラウザclientは接続中、15秒ごとにJSON `{"type":"ping"}`を送り、serverの `{"type":"pong"}` を45秒以内に受信できなければ現在のsocketを閉じ、既存の指数backoff再接続へ遷移する。再接続中は対局操作を無効化する。
- 通常のアイドル対局でも上記のkeepaliveが動く。application pingは既存のmessage rate limitの対象だが、通常間隔は制限値を十分下回る。
- serverのpeerがterminateされると通常の `close` cleanupで接続元枠を解放し、同席のreplacement socketがなければ座席を切断扱いにする。resume/reconnectのreplacementがある場合は、古いsocketのcloseが新しい接続状態を上書きしない。
- serverのheartbeat intervalは30秒、clientのintervalは15秒、clientの応答timeoutは45秒で、設定値はコードに固定している。これはネットワーク死活検知であり、Railway再起動時のインメモリルーム復元や複数プロセス間の状態共有は提供しない。

## WebSocket の abuse control (#641)

Railway のプロセス内で、認証前の `/ws` に次の固定上限を適用する。数値は「4人の通常対局、同一家庭/共有回線、ブラウザの再接続」を許容しつつ、1プロセスのメモリ・CPU・ルーム生成を無制限にしないための第一段階である。

| 対象 | 上限 | 単位/窓 | 超過時 |
|---|---:|---|---|
| 同時 WebSocket 接続 | 256 | プロセス全体 | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 同時接続 | 32 | Node が見た接続元ごと | HTTP 503 + `code: connection_limit` + `Retry-After` |
| 接続試行 | 60 | 接続元ごと / 10秒 | HTTP 429 + `code: rate_limited`, `scope: connection` |
| ルーム作成 | 5 | 接続元ごと / 10分 | WebSocket `error`、`scope: create` |
| ルーム参加 | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: join` |
| 再接続(resume) | 30 | 接続元ごと / 1分 | WebSocket `error`、`scope: resume` |
| メッセージ | 240 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作(`action`/`newGame`) | 120 | WebSocket 接続ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |
| メッセージ合計 | 600 | 接続元ごと / 10秒 | WebSocket `error`、`scope: message`、close `1013` |
| 対局操作合計 | 300 | 接続元ごと / 10秒 | WebSocket `error`、`scope: action`、close `1013` |

上限エラーは機械判定可能な安定コード(`connection_limit` / `rate_limited`)と、再試行までの目安を示す `retryAfterMs` を返す。確立済み接続ではエラー送信後に close `1013`(Try Again Later)で切断し、クライアントは既存の再接続導線から再試行できる。アップグレード前の拒否は WebSocket フレームを送れないため、HTTP ステータス・JSON・`Retry-After` で同じ契約を提供する。拒否したアップグレードソケットと切断済みクライアントは直ちに解放し、期限切れの接続元バケットも定期 sweep で削除する。

接続元はクライアントが自由に指定できるヘッダではなく、Node の `request.socket.remoteAddress`(IPv4-mapped IPv6 は正規化)を使う。したがって、信頼できる proxy の IP 転送設定を前提にしていない。proxy の内側で全利用者が同一アドレスに見える場合でも、256接続のプロセス全体上限と4人対局に十分な接続元上限が残る。現行の `MAX_ROOMS=1,000` とメッセージサイズ上限32 KiBも併用する。

これらは単一 Railway プロセス内の best-effort 制御であり、Railway/外部 proxy の帯域・WAF・分散インスタンス間で共有されるクォータを暗黙に仮定しない。複数インスタンス展開、信頼できる proxy 連携、認証/アカウント単位のクォータ、永続的な観測・ban は別 issue のフォローアップとする。
