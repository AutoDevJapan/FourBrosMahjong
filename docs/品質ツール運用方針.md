# 品質ツール運用方針

[Issue #12](https://github.com/AutoDevJapan/FourBrosMahjong/issues/12) の成果物。Biome / Knip / dependency-cruiser / TypeDoc
の運用方針と除外設定の妥当性を定義する。ツールの物理導入・CI 必須化(PR ブロック)自体は
`.github/workflows/ci.yml` で既に完了済み — 本ドキュメントは「なぜその設定なのか」の根拠を残す。

## 1. 目的・運用方針サマリ

| ツール | 目的 | 運用方針 |
| --- | --- | --- |
| **ESLint**(`pnpm lint`) | 静的解析・バグ/アンチパターン検出 | `next lint` 系ルール(`eslint-config-next` の `core-web-vitals` + `typescript`)を適用する唯一の lint。 |
| **Biome**(`pnpm format` / `check`) | コードフォーマット + import 整列 | **フォーマッタ + assist 専用**。`linter.enabled: false` で lint 機能は使わない。CI ゲートは上位互換の `pnpm check`(§2 参照)。 |
| **Knip**(`pnpm knip`) | 未使用の依存関係・export・ファイルの検出 | Next.js プラグインの自動検出に任せる最小構成。手動 entry 指定はしない(§3 参照)。 |
| **dependency-cruiser**(`pnpm depcruise`) | モジュール間の依存関係検証 | 循環依存を禁止(`error`)。孤立モジュールは注意喚起のみ(`warn`)(§4 参照)。 |
| **TypeDoc**(`pnpm docs`) | `src/` 配下の公開 API ドキュメント生成 | 生成物は非コミット(`docs/api/`, gitignore 済み)。CI ゲートではない(§5 参照)。 |

## 2. Biome と ESLint の役割分担

- **Biome = 整形 + assist のみ**(`biome.json` の `linter.enabled: false` / `assist.enabled: true`)。
  **ESLint = lint のみ**。両方が lint を持つと同じコードに対して矛盾したルール指摘・自動修正の競合が
  起きるため、責務を重複させない(assist は lint ではなく「機械的に一意へ揃える」操作なので競合しない)。
- Biome の担当: インデント・改行・引用符などの機械的な整形(`pnpm format`)、import の並び替え
  (assist の `source/organizeImports`)、CSS の Tailwind v4 `@theme` / ディレクティブ構文への対応
  (`css.parser.tailwindDirectives: true` — `globals.css` の `@theme` ブロックをパースエラーにしないため)。
- ESLint の担当: React/Next.js のベストプラクティス、`core-web-vitals`、TypeScript 型に基づく静的解析。
- **CI ゲートは `pnpm check`(= `biome check .`)**。`biome check` は `biome format` の上位互換で、
  整形に加えて assist も検査する。`linter.enabled: false` なので lint は走らない。
  - 以前は `pnpm format:check`(整形のみ)をゲートにしていたため、**assist の違反 38 件が誰にも検出されず
    たまり、CLAUDE.md / README に載っている `pnpm check` が main で一度も緑にならない**状態になっていた
    (#418)。ステップを増やさず `format:check` を `check` へ置き換えることで解消した(実行時間は
    262 ファイルで約 85ms、`format:check` と同等)。
  - 「ドキュメントが必須ゲートと書いているスクリプトが実際に CI で実行されているか」は
    `src/test/ci-workflow.test.ts` が固定する(スクリプト自体のテストでは検出できない種類の抜け)。
- **`$schema` は CLI の版に追従させる**。ずれていると `biome check` が info を出す。
  `pnpm exec biome migrate --write` で更新できる。
- **除外設定(`files.includes` の `!` 除外)**: `.next/**`, `out/**`, `coverage/**`, `playwright-report/**`,
  `test-results/**`, `docs/api/**` — いずれもビルド・テスト・生成物の出力先で、ソースではないため整形対象外。
  `eslint.config.mjs` の `ignores`(同じ理由づけ、`.next/**` を lint すると `next build` 後に大量の誤検出が出る
  ことが既にコメントで実証済み)と一致させ、Biome 側にも明示することで「なぜ Biome だけ暗黙の `.gitignore`
  依存(`vcs.useIgnoreFile: true`)に頼らず二重に書くか」を明文化した: `.gitignore` は将来的な変更・
  CI 環境でのチェックアウト差分に対して独立でないため、フォーマッタの除外は設定ファイル側にも明示するのが安全。

## 3. Knip の entry/ignore 方針

- `knip.json` は**意図的に最小構成**(`$schema` のみ)を維持する。
- 根拠: Knip は `package.json` の `dependencies`/`devDependencies` に `next` があることを検出すると、
  内蔵の Next.js プラグインを自動適用し、App Router の特殊ファイル(`page.tsx` / `layout.tsx` / `loading.tsx` /
  `error.tsx` / `not-found.tsx` / `route.ts` / `middleware.ts` / `instrumentation.ts` / `next.config.*` など)を
  「フレームワークが暗黙に呼び出すエントリポイント」として自動的に entry 扱いする。実際に
  `pnpm knip` は `src/app/page.tsx` / `layout.tsx` を未使用ファイルとして誤検出しない(検証済み)。
  手動で `entry` を上書きすると、この自動検出よりも狭い/古いパターンで固定してしまうリスクがあるため、
  App Router の規約に追従できる自動検出に委ねる。
- **`ignore` は追加していない**: `docs/api/**` や `coverage/**` などの生成物を明示的に `ignore` へ足すと、
  Knip 自身の config-hint 診断(`pnpm exec knip`)が `Remove from ignore`(`.gitignore` で既にカバーされ
  冗長)と警告することを検証済み — Knip はデフォルトで `.gitignore` を尊重するため、生成物ディレクトリの
  二重指定はノイズにしかならない。Biome/ESLint とは異なり、Knip は自身の設定に対する妥当性チェック機能を
  持つため、そちらの判定を信頼する。

## 4. dependency-cruiser の依存方向ルール

`.dependency-cruiser.cjs` に定義済みの初期案(issue #12 の受け入れ基準の最低ライン):

- **`no-circular`(`severity: "error"`)**: 循環依存を禁止。dependency-cruiser の CLI 終了コードは
  `error` severity の違反件数のみを反映する(`warn`/`info` は違反があっても exit code 0 のまま)ため、
  CI(`pnpm depcruise` を無条件実行)で実際に落とすには `error` である必要がある。当初 `warn` だったが
  本 issue の対応で `error` に引き上げた。
- **`no-orphans`(`severity: "warn"`)**: 「入力(import されている)も出力(何も import していない)も
  ゼロ」の完全孤立モジュールへの注意喚起。デッドコードの**ヒント**であり、アーキテクチャ境界の強制では
  ないため `warn` のまま(壊れているわけではないファイルを CI で強制的に落とすべきではない)。
  Next.js の App Router エントリファイル(`page.tsx` 等)は import 元こそフレームワークの
  ファイルシステムルーティングであり静的解析には映らないが、これらのファイル自身は React/Next の
  API を import しているため `to: {}`(何も import していない)の条件を満たさず、このルールには
  ひっかからない。誤検出リスクは実質ゼロ。
- **除外(`pathNot`)**: `no-orphans` は `\.d\.ts$` と `(^|/)\.[^/]+\.(js|cjs|mjs|ts)$`(dotfile 設定、
  例: `.eslintrc.*` 相当)を対象外にしている。型定義ファイルや設定ファイルは単体で完結しており孤立していて
  当然のため。
- **`no-domain-to-presentation`(`severity: "error"`)**: `src/domain/**` から
  `src/app/**` / `src/components/**` への依存を禁止。「レイヤー間は内向き一方向」の規律のうち、
  最も壊れやすい向き(ドメインが UI を知る)を CI で落とす。
- **`no-components-to-app`(`severity: "error"`)**: `src/components/**` から `src/app/**` への
  依存を禁止。ルートファイルがコンポーネントを組み立てる向きだけを許し、逆辺(再利用可能な UI が
  特定ルートのシェルへ結合する)を防ぐ。
- **レイヤールールの `pathNot`**: 上記 2 ルールは `from` 側から `\.(test|spec)\.tsx?$` を除外している。
  強制対象は**出荷される依存グラフ**であり、ドメインのテストが UI 側のフィクスチャ/ビューモデル写像を
  使って統合的なシナリオを回すのは正当なため(例: `src/components/game/finishedGameFixture.ts` は
  自身を「テスト専用・本番コードからは import しない」と明記している)。本番モジュールに例外は無い。
  実測: `pathNot` を外して cruise すると、この waiver に依存している辺はちょうど 2 本
  (`ai.memo-stability.test.ts → finishedGameFixture.ts` / `engine.ai-actions.test.ts → gameView.ts`)。
- **`no-unresolvable-in-src`(`severity: "error"`)**: `src/` 配下の解決できない import を禁止。
  レイヤールールは「解決できた依存」にしか当たらないが、`src/` は `@/*` エイリアスを多用しており、
  その解決は `options.tsConfig` に依存する。**この設定が外れると `src/` の import 47 件が unresolvable に
  なり、レイヤールールは何にも当たらないまま exit 0 になる**(実測: ドメイン → UI のカナリアを置いても
  `tsConfig` 無しでは exit 0。`no-unresolvable-in-src` を入れると同条件で 156 errors)。
  `from` を `^src/` に限定しているのは、ルート直下のツール設定(`vitest.config.ts` 等)が
  cruise 対象外のモジュールを参照するのは正当なため。
- **`src/` 直下の扱い**: レイヤールールは `src/` 直下のモジュールを対象にしていない
  (`src/proxy.ts` は Next.js の middleware エントリで、`src/app/_lib` の CSP ヘルパを使うのが正当)。
  ここに共有モジュールが増えると `src/domain` → `src/shared` → `src/app` の迂回路が作れてしまうため、
  回帰テストで「`src/` 直下は `proxy.ts` と `global.d.ts` のみ」を不変条件として固定している。
  `src/components/` から CSP/metadata ヘルパを使いたくなった場合は、`src/app/_lib/` から
  レイヤー中立な場所(例: `src/lib/`)へ切り出したうえでルールの対象範囲を見直すこと。
- **見送り理由の解消(issue #382)**: 当初は「`src/` に複数レイヤーが実在してから追加する。存在しない
  フォルダへの path ルールはテスト不能な死んだ設定になる」として見送っていたが、`src/domain/` が
  実装済みになりこの前提は解消した。追加前は「ドメイン層から UI を import するカナリア」を置いても
  `pnpm depcruise` が exit 0 のまま素通りすることを実測しており、追加後は同カナリアで exit 1 になる。
- **ルール自体の回帰テスト**: `src/test/dependency-layers.test.ts`。`pnpm depcruise` は「**今の** `src/` に
  違反が無いこと」しか主張しないため、ルールの削除・`warn` への格下げ・正規表現の空振りは検出できない
  (いずれも違反ゼロのまま exit 0 になる)。このテストは合成したレイヤー構造を一時ディレクトリへ書き出し、
  `.dependency-cruiser.cjs` の `forbidden` をそのまま **dependency-cruiser の `cruise()` に渡して**判定する
  (マッチャを自前で再実装すると本物の挙動から乖離しても気づけないため)。固定するのは
  (1) 逆流 4 種(domain→components / domain→app / components→app / 型のみの import)が `error` severity の
  違反として報告されること、(2) 正方向・テストファイル除外・`src/` 直下の計 7 辺が違反にならないこと、
  (3) ルールが指すレイヤーのディレクトリが実リポジトリに存在し、`src/` 直下に共有モジュールが無いこと、
  (4) 前提条件(解決できない import が error になること・`options.tsConfig` / `tsPreCompilationDeps` の設定)、
  (5) 適用スコープ(`pnpm depcruise` が `src` 全体を対象にし、CI がそれを実行していること)。
  (1)(2) は合成パス上の判定なので、フォルダ名ごと架空の値へ書き換えられた場合は (3) が受け止める。
  実測: 12 種のミューテーション(severity 格下げ / ルール削除 ×3 / `to` の縮小 / `pathNot` 削除 /
  `pathNot` を全 ts へ拡大 / レイヤー名を実在しない値へ / `tsPreCompilationDeps` を false へ /
  `tsConfig` 削除 / depcruise のスコープ縮小 / CI ステップ削除)すべてで red になることを確認済み。

## 5. TypeDoc の対象範囲・出力先

- **対象範囲**: `entryPoints: ["src"]` + `entryPointStrategy: "expand"` — `src/` 配下の全ファイルを走査し、
  **export されているシンボルのみ**をドキュメント化する(TypeDoc の既定動作)。加えて
  `excludePrivate: true` / `excludeInternal: true`(`@internal` タグ付きシンボルを除外)/
  `excludeExternals: true` を明示し、「公開 API のみ」の方針を設定でも保証する。
- **除外**: `**/*.test.ts(x)` / `**/*.spec.ts(x)` — テストコードは公開 API ではなくドキュメント対象外。
- **出力先**: `docs/api/`(`pnpm docs` で生成、`.gitignore` 済み)。ソース管理はしない生成物であり、
  `pnpm docs` を実行した開発者のローカル/CI アーティファクトとしてのみ存在する。
- **CI ゲートではない**: `ci.yml` に `pnpm docs` のステップは無い。ドキュメント生成の失敗は今のところ
  マージをブロックする性質のものではないため(§6 の実行タイミング表を参照)。
- **将来の見直し観測点**: `src/` にライブラリ的な公開境界(例: `src/domain/index.ts` のような barrel)が
  生まれたら、`entryPointStrategy` を `expand` から特定エントリファイルを指す方式に切り替え、
  「本当に外部から使われる API」だけに対象を絞る。現状は Next.js アプリ単体でそのような境界が無いため
  `src` 全体展開が妥当。

## 6. 実行タイミングの切り分け目安(ローカル / pre-commit / CI)

現状 pre-commit フック基盤(husky 等)は未導入。以下は導入する場合の推奨目安、および
`.github/workflows/ci.yml` での実際の運用。

| スクリプト | ローカル | pre-commit(将来導入時の目安) | CI(`ci.yml`) |
| --- | --- | --- | --- |
| `pnpm lint` | 随時 | 推奨(高速) | 必須ゲート |
| `pnpm typecheck` | 随時 | 推奨(高速) | 必須ゲート |
| `pnpm check` | コミット前 | 推奨(`biome check --write` を pre-commit で自動修正する運用も可) | 必須ゲート |
| `pnpm format:check` | `check` に包含されるため通常は不要 | 不要 | **未実行**(`check` が上位互換) |
| `pnpm test` | 随時 | 任意(テスト量が増えたら CI のみに寄せる) | 必須ゲート |
| `pnpm knip` | PR 作成前に 1 回 | 非推奨(全体走査で pre-commit には重い) | 必須ゲート |
| `pnpm depcruise` | PR 作成前に 1 回 | 非推奨(同上) | 必須ゲート |
| `pnpm docs` | ドキュメントを確認したい時のみ | 不要 | 未実行(生成物であり必須ゲートではない) |
| `pnpm test:e2e` | UI 変更時 | 不要(dev server 起動が重い) | 実行(#29 で追加した並列 `e2e` ジョブ。flaky 耐性を考慮し必須ゲートにはしていない) |

CI 列の各ゲートは、変更内容によっては実行されない。何がどの条件で省略され、その検証が
どこで担保されるかは次節を参照。

## 7. CI 実行範囲の絞り込みと、省略した検証の担保先(#491)

Actions の消費時間が実測 **475.7 runner-min / 31.1 時間**(= 約 11,000 min/月)に達したため、
「検証カバレッジを一切減らさずに削れる支出」だけを削る方針で実行範囲を絞っている。

### 7.1 判定を job ではなく step で行う理由

Actions の課金は **job ごとに分単位へ切り上げ**られる。判定用の軽量 job と集約用の gate job を
足す一般的な構成は、判定自体が数秒で終わっても **1 run あたり +2 分**を常に上乗せする。
本リポジトリの実測 job 時間(`ci` 3.9 分 / `e2e` 5.4 分)ではその上乗せがスキップの節約を
ほぼ食い潰すため、判定は各 job の**先頭 step**で行い、重い step だけを `if:` で落とす。

| 方式 | PR 1 件あたりの課金分(加重平均) |
| --- | ---: |
| 判定 job + gate job を追加 | 9.80 |
| **job 内の先頭 step で短絡(採用)** | **8.10** |
| 現行(絞り込みなし) | 11.00 |

この形は副次的に、**required status check が「skip されたまま永久に pending」になる罠を
構造的に回避する** — job 自体は常に実行され常に成功を報告するため、`ci` job そのものが
「変更が無関係でも短時間で成功する安定した gate」として働く。branch protection の
context 名(`lint / typecheck / format / test / build`)を変更する必要もない。

判定ロジックは [`.github/scripts/verification-scope.mjs`](../.github/scripts/verification-scope.mjs)、
不変条件は `src/test/ci-workflow.test.ts` が回帰テストとして固定する。

### 7.2 省略する実行と、その検証の担保先

**検証を消すのではなく、担保先を明示する**。対応が取れないものは省略しない。

| 省略する実行 | 条件 | その検証を何が担保するか |
| --- | --- | --- |
| `ci` / `e2e` の全検証 | 変更が文書のみ(`docs/**` `documents/**` `*.md`。ただし `public/**` と、テストが読むファイルは除く) | 出荷グラフに入るファイルが 1 つも変わらないため、**検証対象が存在しない** |
| `e2e` の Playwright 実行 | 変更が単体テストのみ(`*.test.ts(x)` / `__testing__/` / `__oracle__/`) | production バンドルに入らないファイルのみの変更でブラウザ上の振る舞いは不変。テスト自体の退行は `ci` job の `pnpm test` が検出する |
| `ci` / `e2e` の全検証 | `main` へのマージ後 push **かつ §7.4 のガードが証拠を確認できたとき** | 着地したツリーが、直前に PR の checks が緑にしたツリーと**同一であることを実行時に照合済み**。検証は省略する。共有キャッシュの投入は `main` の `ci` job だけが行い、E2E job は固定Playwrightイメージを使うため setup も省略する(#380, #569) |
| `ci` / `e2e` の全 setup・検証 | 特権昇格経路(`main`→`dev` / `dev`→`stg`)のマージ後 push **かつ §7.4 のガードが証拠を確認できたとき** | PR head と同一の着地 tree は PR 側で検証済み。キャッシュ保存は `main` 限定なので、`dev` / `stg` で依存・ブラウザを導入しても共有できず、setup 自体を省略する |
| Playwright browser の導入 | `main` の検証済みマージ後 push で browser cache がヒット | 検証コマンドは実行せず、復元済みcacheを再導入・再保存する必要もない。cache miss時だけ将来の PR 用に投入する |

**PR での検証は一切省略していない。** 出荷コードを変更する PR(実測で 73.3%)は従来どおり全ゲートを通る。
ローカルでの事前実行(`pnpm lint` / `typecheck` / `check` / `test` / `build`)は CI の代替ではなく、
CI を赤にしてから直す往復を減らすための運用である。

`public/**` は拡張子が `.md` でも「文書」ではない。定義上そのまま配信される出荷ツリーであり、
実際に `public/tiles/CREDITS.md` は `/tiles/CREDITS.md` として配信され Service Worker の
`/tiles/` ランタイムルールの対象にもなる。

また **変更ファイルの取得はリネーム検出を切って行う**(`git diff --name-only --no-renames`)。
git は既定でリネームを検出し移動先のパスだけを出力するため、`git mv src/foo.ts docs/foo.md` が
「文書のみの変更」に化け、**出荷コードが 1 本消えているのに必須ゲートが何も検証せず緑になる**。
分類処理自体は成功しているためフェイルオープンでは救えない。

local の partial checkout は job の実行環境に依存するため、`git diff` で変更パスを解決できない
場合は、同じ immutable SHA 範囲を GitHub Compare API で補完する(#567)。API の rename は
旧パス(`previous_filename`)と新パスの両方を分類し、API エラー・不正な応答・300 件上限に
達して完全性を証明できない場合は従来どおり `unresolved` のまま fail-open して全検証を実行する。
これにより通常は local git の高速経路を使いながら、Playwright container だけが変更パスを
解決できず全 E2E を重複実行する差を解消する。

**文書スキップの落とし穴**: `docs/**` や `*.md` を一律に「文書」と見なすと、テストが内容を
読んでいるファイルまで検証対象から外れる。実際に `src/app/rules/rules-doc.test.ts` は
`docs/四兄弟麻雀ルール.md` を、`src/test/playwright-projects.test.ts` は `README.md` を読んでいる。
これらは `DOCUMENTATION_EXCEPTIONS` として明示的に除外し、**`src/**` 内の
`resolve(process.cwd(), "…")` リテラルを走査して一覧が実態と一致していることを
テストで固定**している(ずれても CI は緑のままで気づけないため)。

判定できない場合(浅い clone・force push・新規ブランチ)は**必ず全検証を実行する**
フェイルオープン。判定不能をスキップ扱いにすると検証の穴が静かに開く。

### 7.3 E2E の並列度

`playwright.config.ts` は `fullyParallel: true` だが、Playwright 既定の `workers: "50%"` は
`floor(cpus × 0.5)` のため **2 コアの GitHub ホスト runner では 1 worker = 完全な直列実行**に
なっていた(CI ログの `Running 143 tests using 1 worker`)。ローカルでは既定の 50% で日常的に
並列実行されており並列安全性は確立済みだったため、CI でのみ worker 数を明示する。

**実際の runner での効果は限定的**であることが実測で判明した。ローカル(8 コア)の測定は
2 コア runner を代表しない — ローカルの「2 worker」は 8 コアを使えるため競合が起きないが、
実際の runner では 2 worker が同じ 2 コアを奪い合う。

| 測定環境 | workers | 実測 | 備考 |
| --- | ---: | ---: | --- |
| ローカル(8 コア) | 1 | 136.2s | CPU 130.7s |
| ローカル(8 コア) | 2 | 71.8s(1.90x) | CPU 138.2s(+6%)。**コア数に余裕があるため過大評価** |
| ローカル(8 コア) | 4 | 59.1s(2.31x) | CPU 169.9s(+30%) |
| **CI(2 コア runner)** | 1 | **266s** | 変更前の実測 |
| **CI(2 コア runner)** | **2** | **243s(1.09x)** | PR #492 の実測。140 passed / 3 skipped、flaky 0 |

CI での実効は **-23 秒(1.09 倍)** に留まる。2 コア runner では 1 worker + Next dev server で
既に CPU がほぼ飽和しており、待ち時間の重なりから取り出せる余地が小さい。
それでも劣化はなく flaky も出ていないため設定は維持するが、**この施策単体で課金分の階段
(切り上げ)を跨ぐ効果は無い**。削減の主体は §7.2 のスキップと重複実行の停止である。

4 worker への過剰購読は、CPU が飽和している以上さらなる短縮は見込みにくく、
競合でタイムアウト耐性を削るため採らない。パーセント指定(`"100%"`)なので runner が
増強されれば自動追従する。

### 7.4 マージ後 push のスキップを実行時に検証する(#496)

§7.2 のマージ後 push のスキップは「永続ブランチに着地した tree は、直前に PR の checks が
緑にした PR head と一致する」という前提に立つ。`main` の通常 PR は branch protection
(`strict: true` / 直 push 禁止 / force push 禁止)で最新baseの取り込みを要求する。一方、実際の
環境昇格は同一repositoryの `main`→`dev` / `dev`→`stg` という特権経路で、各環境に過去の昇格
merge commit が残るため、push前の宛先tipが昇格元headの祖先とは限らない。通常PRの祖先条件を
そのまま昇格へ適用すると、安全側ではあるが毎回証拠不足となり、PRで完了した全検証を再実行する。

そこでガードは branch protection の *設定* を読むのではなく、**検証済みであることの証拠**を
直接確認する。設定がどうであれ、証拠が揃っていれば安全であり、揃っていなければ危険だからである。
副次的に、昇格した権限(`administration:read`)が不要になり、`GITHUB_TOKEN` の
`pull-requests: read` / `checks: read` / `actions: read` だけで済む。

**確認する証拠**(すべて `Resolve verification scope` step の中。job は増やさない):

| # | 証拠 | 何を防ぐか |
| ---: | --- | --- |
| 1 | force push でない(`github.event.forced`) | 履歴の書き換えで前提が丸ごと壊れる |
| 2 | この commit がマージ済み PR の成果物(`merge_commit_sha` と push先baseが一致) | **直 pushで入った未検証コミット**、別branch宛PRの流用 |
| 3 | GitHub Actions が作成した **この workflow / job 自身**の `pull_request` check run が PR head SHA で `success` | required checks を外して緑でないまま入れた PR。同名の別 App / workflow の成功は証拠にしない |
| 4a | `main` の通常PR: push前の `main`(`before`)が PR head の祖先 | `strict` を外して**陳腐化したPR**を入れた場合 |
| 4b | 環境昇格: 同一repositoryの所定経路(`main`→`dev` / `dev`→`stg`)で、push前の宛先tipが landed commit の祖先であることを Compare API (`ahead` / `identical`) で確認 | 任意feature PRによる短絡、古いbase、検証済みhead以外のcommit混入。fast-forward / rebase / squash の履歴形状と正当な環境間の分岐は許容する(#571) |
| 5 | 着地したtreeが PR headのtreeと完全一致 | 3で緑を確認した内容がそのまま入ったことを、commit履歴ではなく内容自体で照合する |

**フェイルセーフ**: どれか 1 つでも確認 **できなかった** 場合(API 失敗・権限不足・ref 取得不可を
含む)はスキップせず全ゲートを実行する。「確認できない」を「安全」と読み替えない。
API と ref 取得には 15 秒の上限を設け、通信停止でも job 全体の timeout まで待たない。
判定結果は `postMergeEvidence=<理由>` としてログに出る(理由は安定した ASCII 列挙)。

実装は [`.github/scripts/verification-scope.mjs`](../.github/scripts/verification-scope.mjs) の
`resolvePostMergeEvidence`。証拠のどれを外しても落ちることを `src/test/ci-workflow.test.ts` が
固定しており、実リポジトリで squash マージと陳腐化マージを再現する統合テストも含む
(マージ後に消える ephemeral な PR ref に依存せず、landed / PR head の commit API と
compare API で証拠を確認する前提は実物でしか確かめられないため)。環境昇格は実際の
`main`→`dev` PR #519 の分岐履歴と `dev`→`stg` を回帰テストに固定し、fast-forward/rebase
形状の dev 昇格 PR #543 (run 31819668038) も検証済み tree と ancestry の証拠に含める。
同runで従来の親配列固定が `merge-parents-mismatch` となり全E2Eを重複実行したため、
Compare API の landed ancestry へ改めた(#571)。証拠が成立した `dev` push run 31523737389 では
検証省略後も `setup=true` だった実測を受け、保存不能なsetupも省略するよう分離した(#523)。
