# 品質ツール運用方針

[Issue #12](https://github.com/AutoDevJapan/FourBrosMahjong/issues/12) の成果物。Biome / Knip / dependency-cruiser / TypeDoc
の運用方針と除外設定の妥当性を定義する。ツールの物理導入・CI 必須化(PR ブロック)自体は
`.github/workflows/ci.yml` で既に完了済み — 本ドキュメントは「なぜその設定なのか」の根拠を残す。

## 1. 目的・運用方針サマリ

| ツール | 目的 | 運用方針 |
| --- | --- | --- |
| **ESLint**(`pnpm lint`) | 静的解析・バグ/アンチパターン検出 | `next lint` 系ルール(`eslint-config-next` の `core-web-vitals` + `typescript`)を適用する唯一の lint。 |
| **Biome**(`pnpm format` / `format:check` / `check`) | コードフォーマット | **フォーマッタ専用**。`linter.enabled: false` で lint 機能は使わない(§2 参照)。 |
| **Knip**(`pnpm knip`) | 未使用の依存関係・export・ファイルの検出 | Next.js プラグインの自動検出に任せる最小構成。手動 entry 指定はしない(§3 参照)。 |
| **dependency-cruiser**(`pnpm depcruise`) | モジュール間の依存関係検証 | 循環依存を禁止(`error`)。孤立モジュールは注意喚起のみ(`warn`)(§4 参照)。 |
| **TypeDoc**(`pnpm docs`) | `src/` 配下の公開 API ドキュメント生成 | 生成物は非コミット(`docs/api/`, gitignore 済み)。CI ゲートではない(§5 参照)。 |

## 2. Biome と ESLint の役割分担

- **Biome = フォーマッタのみ**(`biome.json` の `linter.enabled: false`)。**ESLint = lint のみ**。
  両方が lint を持つと同じコードに対して矛盾したルール指摘・自動修正の競合が起きるため、責務を重複させない。
- Biome の担当: インデント・改行・引用符などの機械的な整形(`pnpm format`)、CSS の Tailwind v4 `@theme` /
  ディレクティブ構文への対応(`css.parser.tailwindDirectives: true` — `globals.css` の `@theme` ブロックを
  パースエラーにしないため)。
- ESLint の担当: React/Next.js のベストプラクティス、`core-web-vitals`、TypeScript 型に基づく静的解析。
- **除外設定(`files.includes` の `!` 除外)**: `.next/**`, `out/**`, `coverage/**`, `playwright-report/**`,
  `test-results/**`, `docs/api/**` — いずれもビルド・テスト・生成物の出力先で、ソースではないため整形対象外。
  `eslint.config.mjs` の `ignores`(同じ理由づけ、`.next/**` を lint すると `next build` 後に大量の誤検出が出る
  ことが既にコメントで実証済み)と一致させ、Biome 側にも明示することで「なぜ Biome だけ暗黙の `.gitignore`
  依存(`vcs.useIgnoreFile: true`)に頼らず二重に書くか」を明文化した: `.gitignore` は将来的な変更・
  CI 環境でのチェックアウト差分に対して独立でないため、フォーマッタの除外は設定ファイル側にも明示するのが安全。

## 3. Knip の entry/ignore 方針

- `knip.json` は**意図的に最小構成**(`$schema` のみ)を維持する。
- 根拠: Knip は `package.json` の `dependencies`/`devDependencies` に `next` があることを検出すると、
  内蔵の Next.js プラグインを自動適用し、App Router の特殊ファイル(`page.tsx` / `layout.tsx` / `loading.tsx` /
  `error.tsx` / `not-found.tsx` / `route.ts` / `middleware.ts` / `instrumentation.ts` / `next.config.*` など)を
  「フレームワークが暗黙に呼び出すエントリポイント」として自動的に entry 扱いする。実際に
  `pnpm knip` は `src/app/page.tsx` / `layout.tsx` を未使用ファイルとして誤検出しない(検証済み)。
  手動で `entry` を上書きすると、この自動検出よりも狭い/古いパターンで固定してしまうリスクがあるため、
  App Router の規約に追従できる自動検出に委ねる。
- **`ignore` は追加していない**: `docs/api/**` や `coverage/**` などの生成物を明示的に `ignore` へ足すと、
  Knip 自身の config-hint 診断(`pnpm exec knip`)が `Remove from ignore`(`.gitignore` で既にカバーされ
  冗長)と警告することを検証済み — Knip はデフォルトで `.gitignore` を尊重するため、生成物ディレクトリの
  二重指定はノイズにしかならない。Biome/ESLint とは異なり、Knip は自身の設定に対する妥当性チェック機能を
  持つため、そちらの判定を信頼する。

## 4. dependency-cruiser の依存方向ルール

`.dependency-cruiser.cjs` に定義済みの初期案(issue #12 の受け入れ基準の最低ライン):

- **`no-circular`(`severity: "error"`)**: 循環依存を禁止。dependency-cruiser の CLI 終了コードは
  `error` severity の違反件数のみを反映する(`warn`/`info` は違反があっても exit code 0 のまま)ため、
  CI(`pnpm depcruise` を無条件実行)で実際に落とすには `error` である必要がある。当初 `warn` だったが
  本 issue の対応で `error` に引き上げた。
- **`no-orphans`(`severity: "warn"`)**: 「入力(import されている)も出力(何も import していない)も
  ゼロ」の完全孤立モジュールへの注意喚起。デッドコードの**ヒント**であり、アーキテクチャ境界の強制では
  ないため `warn` のまま(壊れているわけではないファイルを CI で強制的に落とすべきではない)。
  Next.js の App Router エントリファイル(`page.tsx` 等)は import 元こそフレームワークの
  ファイルシステムルーティングであり静的解析には映らないが、これらのファイル自身は React/Next の
  API を import しているため `to: {}`(何も import していない)の条件を満たさず、このルールには
  ひっかからない。誤検出リスクは実質ゼロ。
- **除外(`pathNot`)**: `no-orphans` は `\.d\.ts$` と `(^|/)\.[^/]+\.(js|cjs|mjs|ts)$`(dotfile 設定、
  例: `.eslintrc.*` 相当)を対象外にしている。型定義ファイルや設定ファイルは単体で完結しており孤立していて
  当然のため。
- **未実装(意図的に見送り)**: 「UI 層 → ドメイン層の一方向」のようなレイヤー間ルールは、`src/` に
  複数レイヤーが実在してから追加する。現状は `src/app/`(Next.js の足場)のみで、`documents/spec/domain-model.md`
  で構想されているドメイン層はまだコード化されていない(CLAUDE.md の "Project state" 参照)。存在しない
  フォルダへの path ルールはテスト不能な死んだ設定になるため、ドメイン層の実装着手時に追加する。

## 5. TypeDoc の対象範囲・出力先

- **対象範囲**: `entryPoints: ["src"]` + `entryPointStrategy: "expand"` — `src/` 配下の全ファイルを走査し、
  **export されているシンボルのみ**をドキュメント化する(TypeDoc の既定動作)。加えて
  `excludePrivate: true` / `excludeInternal: true`(`@internal` タグ付きシンボルを除外)/
  `excludeExternals: true` を明示し、「公開 API のみ」の方針を設定でも保証する。
- **除外**: `**/*.test.ts(x)` / `**/*.spec.ts(x)` — テストコードは公開 API ではなくドキュメント対象外。
- **出力先**: `docs/api/`(`pnpm docs` で生成、`.gitignore` 済み)。ソース管理はしない生成物であり、
  `pnpm docs` を実行した開発者のローカル/CI アーティファクトとしてのみ存在する。
- **CI ゲートではない**: `ci.yml` に `pnpm docs` のステップは無い。ドキュメント生成の失敗は今のところ
  マージをブロックする性質のものではないため(§6 の実行タイミング表を参照)。
- **将来の見直し観測点**: `src/` にライブラリ的な公開境界(例: `src/domain/index.ts` のような barrel)が
  生まれたら、`entryPointStrategy` を `expand` から特定エントリファイルを指す方式に切り替え、
  「本当に外部から使われる API」だけに対象を絞る。現状は Next.js アプリ単体でそのような境界が無いため
  `src` 全体展開が妥当。

## 6. 実行タイミングの切り分け目安(ローカル / pre-commit / CI)

現状 pre-commit フック基盤(husky 等)は未導入。以下は導入する場合の推奨目安、および
`.github/workflows/ci.yml` での実際の運用。

| スクリプト | ローカル | pre-commit(将来導入時の目安) | CI(`ci.yml`) |
| --- | --- | --- | --- |
| `pnpm lint` | 随時 | 推奨(高速) | 必須ゲート |
| `pnpm typecheck` | 随時 | 推奨(高速) | 必須ゲート |
| `pnpm format:check` | コミット前 | 推奨(`format` の write 版を pre-commit で自動整形する運用も可) | 必須ゲート |
| `pnpm test` | 随時 | 任意(テスト量が増えたら CI のみに寄せる) | 必須ゲート |
| `pnpm knip` | PR 作成前に 1 回 | 非推奨(全体走査で pre-commit には重い) | 必須ゲート |
| `pnpm depcruise` | PR 作成前に 1 回 | 非推奨(同上) | 必須ゲート |
| `pnpm docs` | ドキュメントを確認したい時のみ | 不要 | 未実行(生成物であり必須ゲートではない) |
| `pnpm test:e2e` | UI 変更時 | 不要(dev server 起動が重い) | 実行(#29 で追加した並列 `e2e` ジョブ。flaky 耐性を考慮し必須ゲートにはしていない) |
