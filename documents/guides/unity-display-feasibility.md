## 結論

現行リポジトリにはUnity Editor、Unityプロジェクト、`.cs` / `.unity` / `.prefab` / `.anim` 成果物がなく、Unityの実行確認はできない。一方で、Web版には河・手牌遷移・演出・四人回しの表示契約が既にあり、Unityへ渡す表示専用契約を先に固定することは可能である。本番移植の判断に必要なPrefab参照、実機負荷、入力遅延、録画、アセット権利は未検証のため、ここで本番実装へ進めない。

## 表示契約

入力はオンラインの `session` / `snapshot` メッセージに含まれる `OnlineSnapshot` を基礎とする。表示の中心は `snapshot.view: GameViewState` で、`snapshot.version` は同一ルーム内の適用順序を判定するための値として扱う。Unity側は最後に適用した値以下のsnapshotで画面を巻き戻さない。この資料で #818 に含めるのは、この表示契約上のversion適用順序と表示/ルールの責務境界を記録することまでである。

現fixtureの `source.snapshotVersion` は `42` というメタデータ1値だけで、`41 → 42` や `42 → 41` のような具体的なversion sequenceは収録していない。したがって、古いsnapshotを適用しない規則は契約上の制約であり、fixtureがversion sequenceを機械検証した結果ではない。

| Webの値 | Unity表示 | Unityに渡さない責務 |
|---|---|---|
| `view.slots.self/left/across/right` | 4方向の卓スロット | 席割りの導出 |
| `seated.player` | 名前、持ち点、手牌、鳴き、河、北抜き数、状態バッジ | 和了・フリテン・合法性の判定 |
| `bench.player` | 抜け番の名前、持ち点、点差 | 抜け番交代の計算 |
| `tableInfo` | 場風、局、本場、供託、残りツモ、サイコロ、ドラ枚数 | ドラ枚数・局進行の算出 |
| `dora` | 表ドラ/裏ドラの表示 | ドラ翻の計算 |
| `roundSummary` | 和了/流局の結果表示 | 精算、頭ハネ、パオの判定 |
| `players` / `currentTurn` | 接続状態、ホスト、現在手番の表示 | 操作の合法性 |
| `pending` | 原則表示契約外 | 人間/AIの操作決定 |

牌は `suit` / `rank` / `isRed` の表示データとして受け取る。赤ドラの判定、牌山、向聴、フリテン、点数はWeb/Domain側のSSOTに残し、Unityで再実装しない。通信資格情報、transport実装、認証、再接続/resume方式は表示契約の対象外であり、表示fixtureに含めず、後続の `unity/transport` Issueで扱う。

## 4人回しの固定シナリオ

親流れ時は次の変換を必ず使う。旧東は抜け番、旧南は新東、旧西は新南、旧抜け番は新西となる。連荘時は回転せず、本場だけを進める。4局分の回転と、連荘/東4→南1の境界をfixtureで機械検証する。

```text
before: east=P0, south=P1, west=P2, bench=P3
after:  east=P1, south=P2, west=P3, bench=P0
```

東4から南1へ場が変わっても、プレイヤーの持ち点は席移動に伴って移し替えない。局替わり、リロード後の再表示、3人着席+1人抜け番の4パターンは、サーバーから新しい `GameViewState` を受けて同じスロット規則へ投影する。

## Web側で確認できた演出の対応

- `Discards`: 河の順序、狭幅時の折り返し、リーチ宣言牌の横置き、1枚追加時だけの入場cue。
- `HandTileAnimation`: 配牌、ツモ、嶺上/北抜き等の置換、鳴き後の整列を4種類の表示遷移に分類。通常の入場遷移は200ms、配牌の遅延はインデックス由来で決定的。
- `gameEffect` / `EffectOverlay`: 打牌、リーチ、ポン、カン、ツモ、ロン、流局、局終了/半荘終了をコミット済み表示状態から導出。初回描画・リロードは過去イベントとして再演出しない。
- `PlayerSlot` / `GameViewState`: 4物理スロットのうち着席3・抜け番1を明示する。抜け番は席風を持たない。

対応関係と負の契約は `documents/fixtures/unity-display-contract.json` に固定している。

## 権利・アセット境界

OSSの対象コードはMIT表記でも、画像・音声・フォント・Prefab付属素材の再配布権まで自動的に与えるものではない。現行リポジトリの `documents/assets/*/CREDITS.md` も、キャラクター画像とUI原本について権利許諾を独立確認できていないと記録している。したがって、Unityプロトタイプでは仮素材または書面で利用・改変・再配布を確認した素材だけを使う。今回、OSS Assetsのコピー、Majsoul由来素材の取り込み、Unity packageの追加は行っていない。

## 検証手順と証跡

1. Unity Editorが利用可能になった後、候補版の空シーンに仮素材だけを配置する。
2. Unity Editor導入後の手動検証として、固定fixtureの4つの親流れ、連荘据え置き、東4→南1、リロード相当の再適用を再生する。
3. 河の折り返し/リーチ牌横置き、手牌のツモ間隔、席方向、主要演出を確認し、スクリーンショットまたは短い録画を添付する。
4. 入力遅延、フレーム時間、メモリ、ビルドサイズ、実装工数を記録する。
5. ViewModelの外側でルール計算が発生していないことをコードレビューする。

手順上の制約として、「リロード相当の再適用」はUnity Editor導入後に行う手動検証であり、現行Vitestのfixture構造検証には含まれない。現fixtureは `version=42` のメタデータだけを持ち、具体的なversion sequenceを検証していないため、versionの適用順序や古いsnapshotの再適用抑止を確認済みとは扱わない。

今回の実行ではUnity Editorが存在しないため、Unityのスクリーンショット/録画、実機負荷、入力遅延の測定は **未実施** とする。Web側の既存画面ベースラインは `artifacts/ui-screenshots/current-2026-08-25/` にあり、Unity成果物と混同しない。

ローカルの機械検証:

```bash
pnpm exec vitest run src/test/unity-display-contract.test.ts
```

## 次段階のIssue分割案

Go判断が承認された場合に限り、以下を別Issueとして起票する。

1. `unity/prototype`: Editor版固定、仮素材、最小1シーン、スクリーンショット。
2. `unity/transport`: `OnlineSnapshot` のtransport/認証・再接続・resume実装と通信側のversion適用境界。資格情報は表示契約から分離し、#818および本表の工数対象外とする。
3. `unity/performance`: 対象端末の入力遅延、フレーム時間、メモリ、ビルドサイズ。
4. `unity/assets`: 各素材の権利・再配布許諾を独立記録し、未確認素材は本番へ持ち込まない。

これらが揃うまで、Unity版を既存Web版の代替クライアントとして公開しない。
